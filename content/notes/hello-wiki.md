# 把博客搬回 Markdown

动态博客的问题不在于技术新旧，而在于它把写作变成了一件需要维护系统的事。

## 动态博客的三个负担

**内容被锁在数据库里。** 文章存在 MySQL 的 `posts` 表里，改一个错别字要登录后台，想批量替换链接要写 SQL。备份是一个 `.sql` 文件，diff 出来全是二进制噪声。

**主题和插件会腐烂。** 三年前能用的插件，换一个 PHP 版本就报错。你为了写一篇文章，先要修一个依赖。

**写作被界面包围。** 打开后台，左边是菜单，右边是 SEO 评分，上面提示你装一个缓存插件。真正想写的那五百字，反而排在最后。

## 我想要的其实很少

1. 内容是一个个纯文本文件，能用 `git diff` 看见每一次修改。
2. 发布是一条命令，产物是纯静态的 HTML，不依赖数据库和运行时。
3. 链接是稳定的、可读的，十年后还能打开。
4. 支持公式、代码高亮、表格——写技术笔记够用就行。

这正好是 [jyywiki](https://jyywiki.cn/) 的样子。第一次打开它时，最直接的感受是**快**：没有侧边栏推荐，没有弹窗，没有“阅读更多”。一页讲义就是一篇完整的文档，信息密度很高。样式也简单：白底、窄栏、手写体正文、紫色链接，标题和正文之间有清楚的层级。

它让人意识到：个人站点不需要像产品，它更像一本一直放在桌上的笔记本。

## 本站的做法

- Markdown 写在 `content/` 下，一个文件就是一页。
- 一个几百行的 Node 脚本把 Markdown 编译成 HTML，产物在 `dist/`。
- 公式用 KaTeX 在构建时渲染，代码用 highlight.js 着色，都是本地资源，不依赖 CDN。
- `git push` 之后由 GitHub Actions 发布到 Pages。

没有数据库，没有后台，没有评论系统。想改哪句话，直接改对应的 `.md`。

## 代价

这套方案确实少了一些东西：

| 能力 | 有没有 | 说明 |
| --- | --- | --- |
| 评论 | 没有 | 想讨论可以来 GitHub 提 issue |
| 访问统计 | 没有 | 不需要知道谁在看 |
| 全文搜索 | 有 | 构建时生成索引，浏览器里查 |
| 草稿 | 有 | 不提交就是草稿 |

少了这些，换来的是：任何时候 clone 下来都能完整构建，任何编辑器都能写，任何一次修改都有记录。

## 写作流程

```bash
$EDITOR content/notes/some-idea.md
npm run build
git add -A && git commit -m "notes: some idea"
git push
```

如果只是改一句话，连本地构建都可以省掉——GitHub 上的网页编辑器也能直接改 Markdown。

这就是全部。工具应该退到背景里，让内容站到前面。
