# 上下文工程：Agent 的隐形架构

同一个模型，套上不同的提示词、工具和上下文管理策略，完成率可以差出好几倍。真正决定 Agent 上限的，往往不是模型参数，而是**每一步它能看到什么**。

这就是上下文工程：把有限的 token 预算，花在当下最需要的信息上。

## 上下文是预算，不是仓库

模型的上下文窗口越来越大，但“能塞进去”不等于“应该塞进去”。无关内容会稀释注意力，也会让模型更难判断什么重要。

一个实用的分配顺序：

1. **任务与验收标准**：要做什么、怎么算做完。
2. **当前状态**：已经改了什么、哪些验证通过了。
3. **必要资料**：与当前步骤直接相关的代码、文档、报错。
4. **历史摘要**：之前发生了什么，压缩成一两句话。

越靠后的内容越应该被裁剪。完整对话历史是最昂贵的存储方式，也是最不可靠的记忆方式。

## 状态要外置

不要让“做到哪一步了”只存在于对话历史里。对话会被截断，摘要会丢细节，模型会忘。

把状态写进外部载体：

- 一个 `TODO.md` 或任务列表，每完成一步就更新。
- 一个 `notes.md`，记录尝试过但失败的方案，避免重复踩坑。
- 测试、编译、截图等可复现的产物，作为“真的做完了”的证据。

这样即使换一个会话、换一个模型，接手者也能从文件恢复状态。**文件是比上下文更可靠的记忆。**

## 工具输出要裁剪

工具设计里最常见的错误，是把原始输出直接倒进上下文：

```text
$ npm test
... 4,812 行日志 ...
```

Agent 真正需要的可能只有三行：哪个测试失败、错误是什么、涉及哪个文件。工具应该负责把输出变成决策所需的最小信息，而不是把解析工作丢给模型。

一个简单的原则：

> 工具返回的每一行，都应该能改变下一步的动作。

不能改变动作的行，就是噪声。

## 让中间结果可验证

Agent 最容易犯的错不是不会做，而是**以为自己做好了**。

所以每一步都要有验收信号：

- 改代码 → 跑测试、跑类型检查。
- 改页面 → 截图，真的看一眼。
- 改配置 → 启动服务，发一个请求。
- 写文档 → 渲染出来，检查链接。

没有验收信号的“完成”，只是模型的语言习惯。

## 一个循环

```text
观察（读文件 / 跑命令 / 看截图）
  ↓
计划（下一步做什么，为什么）
  ↓
行动（最小的一步修改）
  ↓
验证（测试 / 构建 / 对比）
  ↓
压缩（把结果写进状态文件，清掉无关上下文）
  ↺
```

关键在最后一步。每一轮都把结果沉淀到外部，再带着更短的上下文进入下一轮。上下文会越来越干净，行为也会越来越稳定。

## 常见的反模式

| 反模式 | 后果 | 更好的做法 |
| --- | --- | --- |
| 把整个仓库塞进上下文 | 贵、慢、注意力被稀释 | 先搜索，只读相关文件 |
| 工具返回完整日志 | 关键信息被淹没 | 在工具层过滤、截断、摘要 |
| 没有验收标准 | “做完了”但实际没跑通 | 先定义可执行的检查 |
| 同时改十个地方 | 出问题无法定位 | 小步修改，逐步验证 |
| 目标频繁变化 | 上下文反复重置 | 先写清楚目标，再开始 |

## 结语

模型会继续变强，上下文窗口会继续变大，但“把正确的信息放在正确的位置”这件事不会消失。它更接近软件工程，而不是提示词玄学：定义状态、设计接口、做错误处理、写验收测试。

把 Agent 当成一个需要上下文的合作者，而不是一个需要哄的聊天对象，很多问题会变得清楚。
